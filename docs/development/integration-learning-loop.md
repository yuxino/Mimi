# 持续集成测试与经验积累

这里的“训练”指让项目的验证方法、样本库和回归保护随真实反馈逐次改进。
核心流程是：**固定样本 → 实测 → 定位问题 → 最小修复 → 同样本复测 → 留下回归保护**。
后续对话继续使用这套流程，补充有证据的新经验，并修正已经过时的结论。

## 每轮开始前

1. 检查工作区和远端 main。用户要求最新 main 时，fetch 后核对实际构建
   revision；保留其他分支和未提交工作。记录 clean/dirty，不能把 dirty 构建
   描述成该提交的精确产物。
2. 阅读 [常见回归](common-regressions.md)。macOS 使用
   `./scripts/dev-app.sh` 和 `/Applications/mimi-dev.app`，验证稳定签名、
   bundle identifier、实际进程路径及窗口的 `(dev)` 标记。正式版与开发版
   分开确认；启动成功不代表字幕链路已通过。
3. 检查是否有其他 Mimi 实例占用快捷键或捕获权限。按当前任务协调正常退出，
   不用强杀替代会话收尾，不覆盖身份不同的正式安装。
4. 复用仍有效的编译和下载缓存。先核对缓存位置与并发任务；使用
   `CARGO_TARGET_DIR` 等已有入口，不为了测试清空缓存。对同一工作区的
   前端构建保持顺序，避免自动检查与开发构建相互改写输入。
5. 核对本次实际服务、语言、音频输入、应用捕获范围、代理及保存选项。
   使用当前授权的测试配置；不显示密钥，不借用无关配置的凭据，不为了
   测试自动开启麦克风、字幕保存或音频录制。开发文件凭据按
   [独立开发预设规则](local-dev-credentials.md) 使用。

## 用三类证据完成验证

先写明本轮要验证的问题、样本和预期结果，再开始运行。区分用户观察、
待验证假设和已经证实的缺陷；不能在结果出来后更换通过标准，或把未复现
解释为用户报告无效。保留能揭示失败的样本，成功样本不能替换原失败样本。

| 验证 | 可以支持的结论 | 需要另行验证的部分 |
| --- | --- | --- |
| `./scripts/check.sh` | 当前源码的格式、静态检查、自动测试和前端生产构建结果 | 原生权限、实际服务、可见字幕、其他设备 |
| `--ui-only` 与原生界面检查 | 窗口、布局、控件和对应的本地模拟状态 | 真实捕获与服务响应 |
| 签名 dev 中的真实服务及系统声音样本 | 本次输入经过捕获、识别、翻译并到达原生字幕窗口 | 其他样本、语言、平台和长期稳定性 |

- 识别、文字翻译分别检查连接，记录实际请求耗时。连接检查耗时与字幕
  端到端延迟是不同指标；保留计时边界，不能混用。
- 系统声音使用来源清楚、内容无敏感信息的短样本。先验证音频帧、时长、
  格式和实际播放是否成功，再观察识别、译文和原生浮窗。命令返回零、
  “正在聆听”或 DOM commit 单独都不足以证明整条链路通过。
- 按本轮范围检查启动、暂停、恢复、停止、清空、折叠和长字幕等状态。
  每项留下实际结果；尚未执行、失败和通过分别记录。用户中断时停止操作，
  明确应用与字幕会话是否仍在运行，不继续播放或补做验收。
- 结束测试时，按授权范围停止会话、等待尾部完成，再停止追踪；恢复临时
  设置。中断或收尾失败作为待验证项保留，不能据旧快照宣称完成。

## 从短样本走向可重复的场景库

短合成语音适合先验证链路。质量验证逐步加入真人语音、影视或动画对白、
不同语种与语速、背景音乐、重叠语音、静音及无对白对照；只扩展与当前
问题有关的维度。样本选择规则和 reference 可信度需要明确，不能挑选
容易通过的片段后泛化结果。

- 每个样本保留稳定 ID、来源与使用依据、哈希、时长、格式、标签、
  预期是否有语音和 reference 状态。变速或混音保留父样本及实际参数。
- 私有媒体、reference、音频和字幕取证保存在 Git 外的有界持久目录。
  临时路径中的文件不能作为可重启复用的基线；尚未归档要写明。
- 服务基线与 Mimi 使用可比输入、语言和配置。比较模型输出、后端接纳、
  最终历史及前端显示时，分别记录各层证据和指标。
- 原生系统播放保持串行，避免多份音频混入同一捕获。需要批量服务请求
  时，使用已有有界调度器并遵守本次请求范围。已有场景文档中的并行安排
  不是以后对话启动子代理或付费请求的授权。
- 暂停、清空、恢复、重连测试记录有意排除的时间区间和代次。相同句子
  的重复输入仍有不同身份，不能用文本相同推断回复属于同一次请求。

场景准备与调度沿用 [场景矩阵设计](../plans/2026-10-03-development-scenario-matrix.md)
和 [取证、回放与分析流程](debugger-evidence.md)，不另写一套执行器。

## 根据证据修复

先定位最早出现偏差的阶段：输入／成功发送 → 服务事件 → 后端接纳与
共享核心 → 快照发布 → 各窗口收到和应用 → 原生可见字幕。用事件 ID、
快照 ID、来源、代次和请求身份关联证据；先检查丢失、上限、失败与收尾
状态。缺失证据保留为未知。

普通追踪只收集时序、计数和状态。音频与字幕取证需要明确开启，只存
本机，不自动分享。语义判断需要实际样本与 reference；字数、延迟和
编辑距离不能单独决定翻译是否自然或正确。合成语音也不能替代真人、
音乐背景和真实设备的质量验证。

确认具体不变量和失败边界后才修改产品，保持修复范围最小。公共字幕与
翻译规则放在 `shared/mimi-core`，服务行为遵守共享契约；涉及共享行为
时补充 fixtures，运行直接 Rust 与实际 JNI 检查，按
[平台差异](platform-parity.md) 记录适用范围。

复测先跑原失败样本，再跑容易受影响的相邻场景和必要的自动检查。
前后样本、配置、语言和计时边界保持可比，保留旧结果。一次改善不升级
为“全部解决”；重复复盘只在出现新改动、失败或未解疑点时进行。

## 后续对话如何补充

相关开发、测试或质量排查对话结束前，检查是否产生了新证据或用户明确
要求长期保留的修正。有则更新对应记录、规则和回归保护；没有则保持
现有内容，不为了“积累”重复写相同经验。没有复现的反馈先保留为待验证项，
明确复现条件与下一步；不得直接升级为产品结论。

每次有意义的集成或质量验证结束后，更新 [实测记录](integration-runs.md)：
日期、revision、构建模式、任务范围、样本 ID／类型、配置、验证证据、
失败或未知项，以及下一项具体检查。保持记录简短，不复制完整日志和正文。

把确认能复用的结论写入实际负责该问题的文档或 focused regression：
签名／权限／启动问题进入 `common-regressions.md`，界面反馈问题进入
`ui-guidelines.md`，取证边界进入 `debugger-evidence.md`，平台差异进入
`platform-parity.md`。本页只维护方法，避免把所有经验堆到一个文件。

同一种错误再次发生时，先核查原规则是否被读取、是否足够具体、是否有
真正能拦住失败的测试。把操作条件、失败信号和恢复方式写清楚；能自动
检测的边界加入检查，避免只多写一句提醒。后续可用“相同样本是否仍失败、
重复问题是否被拦住、未验证项是否变少”判断方法有没有加强。

发现旧结论不成立时，注明受影响 revision、条件及新的证据，修正当前
指导；历史记录保留原验证范围。按项目交付规则提交、合并到 main，并
核对远端结果，让其他对话拉取后也能读到更新。

这套流程提供维护规则；捕获、录制、付费批次、修改设置和公开发布仍按
当次用户请求执行，不能把历史经验视为新增操作的授权。
